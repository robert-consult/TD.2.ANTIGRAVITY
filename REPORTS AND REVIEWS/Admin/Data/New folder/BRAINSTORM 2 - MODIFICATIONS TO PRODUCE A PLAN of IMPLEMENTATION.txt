1. MinIO: Storage, Strategy, Lifecycle & Encryption
Your assessment of MinIO is spot on for the first three needs. Here is the concrete strategy for your self-hosted setup:

Bucket Strategy: You only need 1 or 2 buckets. E.g., admin-exports and analytics-artifacts. Use path prefixes (e.g., /trades/, /users/, /compliance/) for organization rather than making endless buckets.
Lifecycle Rules (ILM): Export files shouldn't consume disk space forever. You can configure MinIO Information Lifecycle Management (ILM) to automatically expire and delete objects in the admin-exports/ bucket after 7-30 days. This keeps your bare-metal drives lean without manual cleanup.
Encryption: MinIO supports Server-Side Encryption (SSE). For a free, bare-metal setup, use MinIO KES (Key Encryption Service) backed by a local keystore or HashiCorp Vault. MinIO handles the S3-compatible endpoints seamlessly, allowing your Node app to use standard AWS SDK commands (@aws-sdk/client-s3) pointing to your internal MinIO IP address.
2. Export Job Queue: BullMQ vs. Temporal
You need a system to organize background workers to handle large exports safely. Here is the breakdown and my recommendation for your specific stack:

Feature	BullMQ	Temporal
Dependencies	Valkey or Redis	Postgres + Temporal Server
Learning Curve	Very Low (Native Node.js feel)	Steep (Workflow determinism concepts)
Retry & Backoff	Supported via simple config	First-class, highly advanced
Built-in UI	Requires 3rd-party (e.g., Bull-Board)	Excellent built-in Web UI
Overhead	Very Lightweight	Heavy (requires multiple services)
Alignment Recommendation: BullMQ + Valkey Since you want an easily updatable, free stack and your platform is heavily Node/TypeScript, BullMQ is the better fit. Temporal adds massive operational complexity (managing Temporal Server clusters) which is often overkill unless you have strictly chained, multi-step sagas. BullMQ operating on top of Valkey (the open-source Linux Foundation Redis alternative) keeps memory usage low and execution extremely fast.

3. Worker Instrumentation & Admin UI (Job List, Progress, Cancel, Retry)
The Admin shouldn't just "click and wait." The frontend needs to feel responsive.

Job Tables (Postgres): Create an export_jobs table:
Columns: id, admin_user_id, status (queued, processing, completed, failed), filters_used, progress_percent, total_rows, file_minio_url, created_at, completed_at, error_message.
The UI Flow (Admin Data Tab):
Admin clicks "Export". The UI hits your API endpoint.
The Node API inserts a row in export_jobs (status: queued), pushes a message to BullMQ, and immediately returns the job_id to the UI without waiting.
The Admin Data UI adds a background banner or pop-up widget showing the pending job.
(Optional but ideal) The UI receives progress updates via WebSockets, or simply polls a GET /api/jobs/:id endpoint every 3-5 seconds.
The Admin can click "Cancel" which sets the database flag to cancelled and tells BullMQ to halt the worker.
Worker Instrumentation:
The background worker pulling from BullMQ streams data out of the database.
Every ~10,000 rows, the worker updates the export_jobs table progress_percent and updates the BullMQ job progress state.
Once fully streamed to MinIO, the worker generates a short-lived Pre-Signed S3 URL, saves it to the row, and marks the job completed. The UI can then immediately offer this URL as a download link.
4. ClickHouse Integration (Analytics Plane)
To handle billions of rows effortlessly, Postgres will inevitably bottleneck on GROUP BY and aggregate queries.

How it fits in: ClickHouse is an incredibly fast, open-source columnar database built precisely for OLAP (analytics).
Integration Method: You don't need their paid cloud. You will install the ClickHouse server bare-metal alongside your backend.
Data Pipeline Strategy: Use ClickHouse's built-in PostgreSQL Table Engine / Materialized Dictionaries or a simple background worker to silently sync trades from Postgres into ClickHouse. Postgres remains your source of truth; ClickHouse acts as the analytics replica.
The Admin UI queries ClickHouse for "win rates," "volume," and "PnL" dashboards, which will load in milliseconds. Huge export jobs can also hit ClickHouse to rapidly stream raw data out to MinIO.

6. Gap Map Improvements & Document Critique
Looking closely at the gap map provided in the initial text, here are a few improvements and critical blind spots you should address:

(Improvement) File Format: Don't default to pure CSV for billions of rows if you don't have to. Offer Parquet streams or JSONL. Parquet is natively supported by ClickHouse, highly compressed, and Node libraries can generate it efficiently. It saves massive MinIO disk space.
(Improvement) Streaming, not Bounding: Your BullMQ workers must use database cursors (e.g., Node Postgres streams). If you attempt to load 10 million rows into Node's memory to map them before piping to MinIO, the Node process will crash (Out of Memory). You must stream directly from the DB cursor => line transform => MinIO multipart upload.
(Blind Spot) Zombie Jobs: If a worker crashes mid-export, you need a mechanism to detect jobs stuck in processing for too long and auto-retry or mark them as failed. BullMQ handles stalled job recovery, but your Postgres export_jobs table state needs to ensure it eventually syncs up.
(Blind Spot) Disk Spoilage on ClickHouse: While ClickHouse is incredibly fast, it consumes disk rapidly if not partitioned properly. Ensure you set up table sorting keys and chronological partitioning (e.g., PARTITION BY toYYYYMM(created_at)) from Day 1 so you can drop extremely old partitions easily without doing heavy DELETE queries.
