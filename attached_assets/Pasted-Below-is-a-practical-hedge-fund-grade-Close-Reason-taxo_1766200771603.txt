## Additional close reasons you should include (common in production platforms)

### 1) Margin and liquidation (must-have)

| Code       | UI label               | When it applies                                                             |
| ---------- | ---------------------- | --------------------------------------------------------------------------- |
| `STOP_OUT` | Stop out / liquidation | Broker/platform auto-closes due to insufficient margin (forced liquidation) |

Why it matters: This is one of the most important “non-user” closures for risk governance. In MetaTrader-style ecosystems this is a first-class reason (`DEAL_REASON_SO`). ([MQL5][1])

### 2) Strategy / automation / system-initiated closes

| Code     | UI label             | When it applies                                                                              |
| -------- | -------------------- | -------------------------------------------------------------------------------------------- |
| `EXPERT` | Strategy / bot close | Closed by an automated strategy / EA / internal algo                                         |
| `SYSTEM` | System safeguard     | Closed by platform logic (non-strategy) to protect integrity (e.g., stale-feed safety close) |

MetaTrader explicitly distinguishes client vs expert/bot vs web/mobile channels in “deal reason” style fields. ([MQL5][1])

### 3) Admin / compliance / account-status enforced closes

| Code             | UI label             | When it applies                                             |
| ---------------- | -------------------- | ----------------------------------------------------------- |
| `ADMIN`          | Admin close          | Admin forcibly closes a position                            |
| `COMPLIANCE`     | Compliance close     | KYC/AML/compliance enforcement close                        |
| `ACCOUNT_FROZEN` | Account frozen close | Forced close because account moved to Frozen/Disabled state |

These become essential once you add “View as Trader,” freezes, and institutional audit expectations.

### 4) Risk-policy closures (your platform’s guardrails)

If you already enforce trade limits, it’s standard to also support forced closures when limits are breached or when a risk kill-switch is triggered.

| Code         | UI label         | When it applies                                                                              |
| ------------ | ---------------- | -------------------------------------------------------------------------------------------- |
| `RISK_LIMIT` | Risk limit close | Closed due to a risk rule (daily loss limit, max drawdown, exposure cap, max lots cap, etc.) |

This should carry **details** like `ruleId=MAX_TOTAL_LOTS`, `threshold=50`, `observed=52`.

### 5) Instrument/session lifecycle (depends on products)

| Code       | UI label         | When it applies                                             |
| ---------- | ---------------- | ----------------------------------------------------------- |
| `EXPIRY`   | Contract expiry  | Instrument expires (futures/CFD expiry logic)               |
| `ROLLOVER` | Rollover         | Position closed/reopened due to rollover (where applicable) |
| `SPLIT`    | Corporate action | Corporate action / split handling (mostly equities/CFDs)    |

MetaTrader ecosystems explicitly model rollover/variation margin/split as execution reasons. ([MQL5][1])

## Feedback on enhancing the list (important design guidance)

### 1) Split “reason” into **Reason Code** + **Reason Details**

**Do not** try to encode everything into one label. Use:

* `closeReasonCode` (stable enum)
* `closeReasonDetail` (JSON/text: ruleId, channel, margin level, duration, etc.)

This is the difference between “nice UI” and “audit-grade.”

### 2) Capture **initiator** separately from **trigger**

A strong model is:

* **Initiator**: `USER | ADMIN | SYSTEM | STRATEGY`
* **Trigger**: `MANUAL | SL | TP | STOP_OUT | RISK | EXPIRY | …`

MetaTrader’s separation of “deal reason” variants (client/web/mobile/expert vs SL/TP/SO) is effectively pointing to the same concept. ([MQL5][1])

### 3) Avoid ambiguity for SL/TP detection

When SL/TP is hit, store:

* the **target price** that was active at the time
* the **fill price**
* any **slippage**
  This prevents disputes when price gaps or spread spikes occur.

### 4) UI/UX: treat Close Reason like your BUY/SELL pill

* Render as a compact badge (“Stop Loss”, “TP”, “Stop Out”, “Risk Limit”).
* Hover tooltip reveals detail (ruleId, hold time, margin level).

### 5) Reporting/export alignment

Export should include:

* `closeReasonCode`
* `closeReasonLabel`
* `closeInitiatorType`
* `closeInitiatorUserId` (nullable)
* `closeChannel` (web/mobile/api/strategy)
* `closeReasonDetail`
