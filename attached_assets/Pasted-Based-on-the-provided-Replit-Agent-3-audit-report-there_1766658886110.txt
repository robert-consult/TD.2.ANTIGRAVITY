## 1) Critical failures (must be corrected)

### A) **Contender tier enum drift (“CONTENDER” is not a valid contenderTier)**

The report asserts `PERFORMER` maps to `contenderTier = "CONTENDER"` and that demotion to PERFORMER sets `contenderTier = "CONTENDER"`. 

Your context spec defines contenderTier values as **NONE / CANDIDATE_SMS_REQUIRED / VERIFIED_SMS** (optionally SELECTED_REAL_CAPITAL), and tier updates are algorithmic (eligibility ⇒ CANDIDATE_SMS_REQUIRED; SMS verified ⇒ VERIFIED_SMS). There is **no “CONTENDER” contenderTier state**. 

**Impact**

* UI/back-end gating can silently diverge (feature appears unlocked/locked incorrectly).
* PolicyDecision can deny/allow incorrectly if it expects one enum set while DB stores another.

**Required correction**

* Keep **userTier** (CANDIDATE / PERFORMER / SELECTED) separate from **contenderTier** (NONE / CANDIDATE_SMS_REQUIRED / VERIFIED_SMS / SELECTED_REAL_CAPITAL).
* Remove any assignment of contenderTier = `"CONTENDER"`. Use:

  * contenderTier = NONE by default
  * contenderTier = CANDIDATE_SMS_REQUIRED only when eligibility rules pass
  * contenderTier = VERIFIED_SMS only after SMS verified

### B) **KYC status model drift (PENDING/INVITED vs SUBMITTED/APPROVED etc.)**

The report defines `user_kyc_profiles.status` as **NOT_STARTED, INVITED, PENDING, APPROVED, REJECTED**, and describes user submission as “PENDING.” 

Your earlier UI plan and stubs used **SUBMITTED** (not PENDING), and your policy/tier context references KYC gating in a way that expects consistent, stable status semantics. 

**Impact**

* Frontend cards (KYC Status / Payout) can display wrong states.
* Admin queue filters/reviews can mismatch actual statuses stored.
* PolicyDecision can deny KYC view/submit incorrectly.

**Required correction**

* Choose one canonical enum set and apply it everywhere (DB, API, UI, PolicyDecision).
* If you keep INVITED, then the typical minimal set is:

  * NOT_STARTED → INVITED → SUBMITTED → APPROVED/REJECTED
    (or NOT_STARTED → INVITED → PENDING → APPROVED/REJECTED, but then UI must use PENDING everywhere)

### C) **KYC gating contradicts your “invite-based” invariant**

The report says `KYC_VIEW` and `KYC_SUBMIT` check only that user is `SELECTED` tier. 

Your model explicitly requires KYC to be **invite-based** (selected/eligible does not automatically mean KYC is visible unless invited). 

**Impact**

* Selected traders could see KYC without being invited (policy drift).
* UI/back-end can diverge if UI hides KYC while API allows it (or vice versa).

**Required correction**
PolicyDecision for KYC must require **both**:

* `userTier === SELECTED` **and**
* `kycStatus in {INVITED, SUBMITTED/PENDING, APPROVED}` (or `kycInvitedAt != null`)
