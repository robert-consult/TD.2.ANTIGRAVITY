1) The correct “single stream” architecture for uniform symbols
A. One ingest point, one internal stream
Quote Ingestor (singleton):

Polls (or receives WS) from your upstream feed once.

Maintains the latest quotes map in memory.

Publishes updates to an internal pub/sub channel, e.g. quotes:delta (or quotes:batch).

WS/API pods (replicas):

Subscribe to the internal quotes:* channel.

This is still “one stream” from the client’s perspective, even though you have multiple pods: every pod broadcasts the same message to the clients connected to it.

2) Why “single stream” does not automatically mean “cheap”
Even with one stream, your cost is dominated by outbound bandwidth:

Outbound Mbps ≈ (bytes_per_update × updates_per_second × concurrent_clients × 8) / 1,000,000

So your objective is to minimize bytes_per_update and updates_per_second (while keeping the trading UI responsive).

3) Best practice for a single-stream payload: “batch + delta + throttle”
Because all clients see the same instruments, the most efficient pattern is:

1) Server ingests at full fidelity (internal)
You keep high-frequency updates inside the platform for trading logic.

2) Server broadcasts to clients at a controlled UI frequency (external)
Broadcast at a fixed UI cadence (e.g., 2–5 Hz), not on every upstream tick.

Each broadcast is either:

Delta batch: only symbols changed since last broadcast window, or

Compact batch snapshot: all symbols but encoded tightly (often simpler and comparable in size if “most symbols change anyway”).

At scale, the silent killer is buffering. A portion of clients will be slow (mobile, congested networks). If you queue, you explode memory and latency.

Best practice:

If a socket is behind, drop intermediate quote messages and only keep “latest”.
