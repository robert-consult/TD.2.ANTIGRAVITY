# Replit Agent 3 — Hedge-Fund-Grade Identity, Verification, Gating, KYC, and Audit Implementation Checklist (File-by-File)

This is the **agent-executable** checklist to audit (and close gaps) for the full system you specified: **email verification from signup (Resend) → rolling re-verification → SMS (Twilio Verify) contender gating → tiered access (Profile Settings/KYC/Payout) → sessions/devices termination → admin dashboards (Audit Trail + KYC Queue) → complete end-to-end audit capture**.

It is written to be used **component-by-component, route-by-route, table-by-table**, matching your “progressive confirmations” model and the “hedge-fund-grade” requirement.

---

## 0) Ground Rules and Acceptance Criteria (release-blockers)

### 0.1 Single source of truth

* [ ] **All gating decisions** must flow from `shared/policyDecision.ts` (not duplicated logic across UI/routes).
* [ ] UI is allowed to *mirror* decisions for UX, but the server must always enforce the same decision.

### 0.2 Deterministic enforcement (must be true always)

* [ ] **Email verification grace window**: allow trading for a fixed grace period from signup (per spec).
* [ ] **After grace**: block exposure-increasing actions until email verified.
* [ ] **Rolling re-verification**: after verification, a reverify due date exists; overdue reverify eventually blocks.
* [ ] **SMS is never required at signup**: only required/available once user meets contender thresholds (tier gating).
* [ ] **KYC + payout are invite/selected-tier only** (not universal).
* [ ] **All identity changes and attempts** emit `identity_audit` events with tamper-evident chaining.

### 0.3 UX must be consistent

* [ ] Profile Settings shows real data for:

  * Recent Login Activity (from login history trail)
  * Active Sessions (from sessions table)
  * Logout other devices / terminate device session works and immediately invalidates
* [ ] Timezone list is **canonical**: `(UTC±HH:MM)` prefixed, DST-aware, city-rich.
* [ ] Language selection is persisted and applied; (full app i18n execution is in a separate checklist item set—still referenced below for tie-in to email/SMS templates).

## 1) Data Model Checklist (tables, columns, invariants)

> Primary schema file: `shared/schema.ts`
> Schema enforcement/patching: `server/db/ensureSchema.ts` (and any ensure helpers used at boot)

### 1.1 `users`

Verify (at minimum) these are present and used end-to-end:

* [ ] `firstName`, `lastName`, `username` (or display name), `email`
* [ ] `timezone`, `language`, `country`
* [ ] Tier fields used for progressive confirmations: `userTier` (or equivalent)
* [ ] Anything used for contender thresholds (starting equity, balance, createdAt, etc.)

**Invariants**

* [ ] Updating timezone/language/country must persist to `users`, and UI must reload it after save.
* [ ] Username uniqueness enforced (DB + API).

### 1.2 `user_verification`

Verify the identity state machine storage exists:

* [ ] `emailVerifiedAt`
* [ ] `emailVerificationTokenHash` (hash only; never store raw token)
* [ ] resend throttles: `emailLastResendAt`, `emailResendCountDay`, `emailResendDayStart`
* [ ] rolling reverify: `emailReverifyDueAt`
* [ ] SMS verify: `smsVerifiedAt`
* [ ] SMS throttles/lock: `smsOtpFailCount`, `smsOtpLockedUntil`, `smsLastSendAt`, `smsSendCountDay`, `smsSendDayStart`
* [ ] contender tier enum / progression marker (e.g., `contenderTier`)

**Invariants**

* [ ] Changing email resets verification state and issues new token.
* [ ] email verify success sets `emailReverifyDueAt`.

### 1.3 `user_sessions`

Verify:

* [ ] unique `sessionId` (string), `userId`
* [ ] `createdAt`, `lastActiveAt` (or lastSeenAt)
* [ ] `ip`, `userAgent`, optional device parsing fields (`deviceType`, `browser`, `os`)
* [ ] revocation: `revokedAt`, `revokedByUserId`, `revokeReason`

**Invariants**

* [ ] **Every login** creates a row.
* [ ] **Every authenticated request** updates `lastActiveAt` (touch).
* [ ] Revoked/ended sessions are rejected by auth middleware (non-static session enforcement).

### 1.4 `user_login_history`

Verify:

* [ ] `eventAt` (or consistent time field)
* [ ] `success`, `ip`, `userAgent`, `sessionId`
* [ ] optional failure reason

**Invariant**

* [ ] both successes and failures recorded.

### 1.5 `identity_audit` (tamper-evident chain)

Verify:

* [ ] `prevHash` and `eventHash`
* [ ] event taxonomy covers EMAIL/SMS/MFA/KYC/SESSION/ADMIN
* [ ] event payload supports `actorUserId`, `targetUserId`, `sessionId`, `ip`, `userAgent`, `reason`, and any decision context IDs.

**Invariants**

* [ ] Every verification send/verify attempt produces an audit record (success + failure).
* [ ] Admin actions produce audit records.

### 1.6 KYC & payout profile

Verify:

* [ ] `user_kyc_profiles` with statuses and timestamps (invited/submitted/reviewed)
* [ ] `user_payout_profiles` gated behind KYC approval + selected tier
* [ ] all changes audited

* [ ] Insert happens in a single transaction or in a consistent sequence.

**Audit coverage**

* [ ] Called by:

  * session revoke / logout / login events
  * MFA enable/disable events

## 9) Backend — Verification routes (Resend + Twilio)

### File: `server/routes/verification.ts`

This is your identity engine surface. Audit all routes, and cross-check they map to policy decisions and write audit rows.

#### 9.1 Email send/resend

Checklist:

* [ ] Endpoint exists:

  * [ ] `POST /api/verification/email/send` (or `/email/resend`)
* [ ] Generates token, stores only `emailVerificationTokenHash` (HMAC/sha256).
* [ ] Uses Resend API (must succeed with real send).
* [ ] Enforces:

  * [ ] cooldown
  * [ ] per-day cap per user
  * [ ] optional per-IP cap
* [ ] Emits `identity_audit`:

  * EMAIL_SEND_REQUESTED
  * EMAIL_SEND_SUCCEEDED / EMAIL_SEND_FAILED

#### 9.2 Email verify

Checklist:

* [ ] Endpoint exists:

  * [ ] `GET /api/verification/email/verify?token=...` (or POST)
* [ ] Token is compared against stored hash safely.
* [ ] On success:

  * [ ] set `emailVerifiedAt`
  * [ ] set `emailReverifyDueAt = now + reverifyInterval`
  * [ ] clear `emailVerificationTokenHash`
  * [ ] emit audit EMAIL_VERIFIED
* [ ] On failure:

  * [ ] emit audit EMAIL_VERIFY_FAILED

#### 9.3 Re-verification

Checklist:

* [ ] There is a reverify path (same verify endpoint is fine, but state must reflect due/overdue).
* [ ] Policy engine reads due date and blocks when overdue beyond threshold.
* [ ] Reminders / scheduled nudges exist if included in your spec (see cron section below).

#### 9.4 SMS (Twilio Verify) start

Checklist:

* [ ] Endpoint exists:

  * [ ] `POST /api/verification/sms/start`
* [ ] Enforced by policy:

  * [ ] Only contender-eligible
  * [ ] Email must be in good standing (verified and not overdue)
* [ ] Enforces OTP send caps and cooldown.
* [ ] Emits audit SMS_SEND_REQUESTED / SMS_SEND_SUCCEEDED / SMS_SEND_FAILED

#### 9.5 SMS (Twilio Verify) confirm

Checklist:

* [ ] Endpoint exists:

  * [ ] `POST /api/verification/sms/confirm`
* [ ] On success:

  * [ ] set `smsVerifiedAt`
  * [ ] update contender tier progression (if model includes)
  * [ ] emit audit SMS_VERIFIED
* [ ] On failure:

  * [ ] increments fail count
  * [ ] locks after threshold (`smsOtpLockedUntil`)
  * [ ] emit audit SMS_VERIFY_FAILED and SMS_LOCKED (when applicable)

## 18) “Proof” Queries Agent 3 should run in SQLite after each test

Use these to prove the system is truly writing state and trails:

```sql
-- Verification state
SELECT * FROM user_verification WHERE user_id = ?;

-- Sessions
SELECT session_id, user_id, created_at, last_active_at, revoked_at, revoke_reason
FROM user_sessions WHERE user_id = ? ORDER BY last_active_at DESC;

-- Login history (verify timestamp fields align to UI)
SELECT * FROM user_login_history WHERE user_id = ? ORDER BY event_at DESC LIMIT 20;

-- Identity audit (confirm hash chaining, event taxonomy)
SELECT id, at, category, type, actor_user_id, target_user_id, prev_hash, event_hash
FROM identity_audit WHERE target_user_id = ? ORDER BY id DESC LIMIT 50;

-- KYC
SELECT * FROM user_kyc_profiles WHERE user_id = ?;

-- Payout
SELECT * FROM user_payout_profiles WHERE user_id = ?;
```
