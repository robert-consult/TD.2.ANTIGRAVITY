1) Objectives and principles
Core intent

Minimize signup friction: allow immediate account creation and platform access.

Maintain integrity over time: enforce email verification after a 2-week trading grace window.

Reduce “temporary email” abuse: require monthly re-verification so throwaway emails naturally expire.

Spend on SMS only where it matters: SMS verification is a “serious contender” gate, not a default.

Operational principles

Make enforcement stateful and auditable (clear account status, timestamps, and reasons).

Use progressive enforcement: remind → restrict → lock.

Keep user messaging predictable: exact dates, countdown, what actions are blocked.

Due - 7 days

Due - 3 days

Due - 1 day

Due day

Due + 2 days (within grace; final warning)

T2) No overlapping cycles per user + cycle_type

Prevents double-counting in funnel.

Rule: for same (user_key, cycle_type) cycles must not overlap:

next.cycle_start_at >= current.due_at (or >= current.cycle_start_at if using event-defined boundaries)

Skeleton:

-- tests/custom/test_no_overlapping_cycles.sql
with ordered as (
  select
    user_key,
    cycle_type,
    cycle_start_at,
    due_at,
    lead(cycle_start_at) over (partition by user_key, cycle_type order by cycle_start_at) as next_start
  from {{ ref('fct_verification_cycle') }}
)
select *
from ordered
where next_start is not null and next_start < due_at;

2) Migration playbook for introducing monthly re-verification without disrupting existing users

This assumes you already have users in the platform and want to introduce:

“verify post-signup with 14-day trading grace”

“monthly re-verification”

“SMS only for contenders”

Phase 0 — Inventory and policy decisions

Before touching production, decide these two critical migration policies:

P0.1 Existing unverified users: avoid immediate lock

If there are accounts older than 14 days that never verified, your new rule would lock them instantly.

Migration must create a fresh grace window for them.

Recommended policy

For any existing user with emailVerifiedAt = null, set:

emailInitialDueAt = now + 14 days (not createdAt + 14)

accountState = ACTIVE_UNVERIFIED_GRACE until that due date

P0.2 Existing verified users: start reverify cycle gently

If you don’t have a reliable “last verified” timestamp, do not retroactively declare them overdue.

Start everyone with a fresh cycle.

Recommended policy

For any existing user with emailVerifiedAt != null, set:

emailReverifyDueAt = now + 30 days (or staggered rollout by cohort)

accountState = ACTIVE_VERIFIED

This prevents a surprise lockout wave.

Goal: ship the plumbing without restricting users.

Add columns (nullable) and seeds:

events are flowing

banners render correctly

Phase 2 — Backfill and due-date initialization

Goal: populate due dates/states for all existing users safely.

Backfill rules (recommended):

2.1 For users with no emailVerifiedAt

Set emailInitialDueAt = now + 14 days

Set accountState = ACTIVE_UNVERIFIED_GRACE

2.2 For users with emailVerifiedAt present

Set emailReverifyDueAt = now + 30 days

2.3 For users in weird/unknown states

Why CRC32

widely available in Node, Python, and many SQL engines

simple and fast for bulk updates

deterministic across languages when implemented correctly on bytes

Canonical CRC32 procedure

Build the input string exactly:

Encode as UTF-8 bytes.

Compute CRC32 on bytes.

Convert to unsigned 32-bit integer.

Unsigned handling

4) Reference implementations (short and exact)
4.1 Node/TypeScript (recommended for your stack)

Use a CRC32 library (many exist). The key is to treat it as unsigned.

Logic (conceptual, not tied to a specific package):

crc = crc32(Buffer.from("reverify-v1|" + userId, "utf8"))

u32 = crc >>> 0

jitterDays = u32 % 15

4.2 Python

Python’s zlib.crc32 is standard.

u32 = zlib.crc32(data) & 0xffffffff

jitterDays = u32 % 15

4.3 SQL (options)

SQL support varies; three patterns:

Option A: Database has CRC32 built-in (ideal)

jitterDays = CRC32(CONCAT('reverify-v1|', user_id)) % 15

Option B: Database supports MD5 but not CRC32
Use MD5 and take a subset of hex as int (stable but slightly more work):

hashHex = MD5('reverify-v1|' || user_id)

u32 = hex_to_int(substr(hashHex, 1, 8))
