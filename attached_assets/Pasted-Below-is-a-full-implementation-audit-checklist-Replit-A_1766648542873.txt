Below is a **full, implementation-audit checklist** Replit Agent 3 can use to cross-check end-to-end completion. It is written to be **deterministic and testable** (pass/fail), aligned to your **tiered gating invariants**, and scoped to: **email validation (initial + resend + rolling revalidation), SMS validation (Twilio), KYC (invite-based + Selected tier), profile settings (trader + admin), audit/data trails (hedge-fund-grade), and admin mini-tabs wiring (additions-only)**.

---

## A. Global invariants and non-negotiables (must hold everywhere)

### A1) Single-source-of-truth gating (no UI/backend drift)

* [ ] `shared/policyDecision.ts` exists and is imported by:

  * [ ] Server routes (trade mutations, email resend, sms, kyc)
  * [ ] Frontend gating (Profile Settings, header dropdown, KYC/Payout panes)
* [ ] Every deny returns `{ deny_code, accountState }` (or at least `deny_code`) consistently.
* [ ] A “decision matrix” endpoint or `GET /api/profile/me` returns sufficient fields so client can compute the same gating decisions without guessing.

### A2) Server-side enforcement precedes all engine actions

* [ ] **All** trade actions that affect exposure call `decidePolicy()` before risk engine checks:

  * [ ] Market open / increase
  * [ ] Pending placement
  * [ ] SL/TP modify (with risk-reducing intent if supported)
* [ ] Reduce-only actions remain allowed per policy:

  * [ ] Close / reduce
  * [ ] Cancel pending (if configured as allowed while locked)

### A3) Additions-only rule

* [ ] No existing top tabs removed/renamed.
* [ ] No existing mini-tabs removed/renamed.
* [ ] New tables/columns added without breaking current Drizzle schema compilation.

## B. Email validation requests (initial verification)

### B1) Required user states

* [ ] New signups create/ensure a `user_verification` record (idempotent).
* [ ] State model exists in policy:

  * [ ] `ACTIVE_UNVERIFIED_GRACE` (0–14 days)
  * [ ] `LOCKED_EMAIL_UNVERIFIED` (>14 days with no verify)
  * [ ] `ACTIVE_VERIFIED`
  * [ ] `LOCKED_EMAIL_REVERIFY_OVERDUE` (verified but overdue beyond rolling window + grace)
  * [ ] `SUSPENDED_ADMIN` (frozen/disabled equivalent)

### B2) Initial verification request flow (Resend integration)

* [ ] Endpoint exists: `POST /api/auth/email/send-verification` OR `POST /api/profile/email/resend` (exact name is OK; must exist).
* [ ] Endpoint enforces policy action: `EMAIL_RESEND_VERIFICATION`.
* [ ] Uses **Resend** to deliver verification email with:

  * [ ] signed token / code
  * [ ] expiry timestamp
  * [ ] correlationId (optional but recommended for audit)
* [ ] Verify endpoint exists: `GET /api/auth/email/verify?token=...` (or POST), and:

  * [ ] sets `emailVerifiedAt`
  * [ ] sets/refreshes `emailReverifyDueAt = now + 30 days`
  * [ ] emits an audit event `EMAIL_VERIFIED`

### B3) Enforcement behavior

* [ ] If `LOCKED_EMAIL_UNVERIFIED`, server denies exposure-increasing trade actions with:

  * [ ] HTTP 403 + `deny_code: EMAIL_UNVERIFIED_GRACE_EXPIRED`
* [ ] UI displays lock banner and blocks trade UI actions consistent with policy.

### B4) Anti-abuse throttles (email resend)

* [ ] Cooldown enforced (e.g., 60s) → returns `EMAIL_SEND_COOLDOWN`.
* [ ] Daily cap enforced (e.g., 5/day) → returns `EMAIL_SEND_RATE_LIMIT`.
* [ ] Counters stored:

  * [ ] `emailLastResendAt`
  * [ ] `emailResendCountDay` (+ day bucket / reset logic)

### B5) Audit trail coverage (hedge-fund grade)

For each email event:

* [ ] `EMAIL_VERIFICATION_SENT`
* [ ] `EMAIL_VERIFICATION_SEND_DENIED` (rate limit / cooldown)
* [ ] `EMAIL_VERIFIED`
* [ ] `EMAIL_LOCK_APPLIED` (when lock state triggered or first detected)
  Captured fields:
* [ ] userId, email, username
* [ ] ip, userAgent, sessionId (if available)
* [ ] timestamp (ms)
* [ ] event_hash + prev_hash if using hash chain for identity audit (recommended)

## C. Email rolling revalidation requests (30-day reverify policy)

### C1) Rolling reverify state

* [ ] On successful email verification, `emailReverifyDueAt = now + 30 days`.
* [ ] `emailReverifyDueAt` is evaluated every request (no reliance on cron correctness).

### C2) Overdue handling

* [ ] Grace after overdue exists (configurable, e.g., 5 days).
* [ ] After `emailReverifyDueAt + overdueGrace`, trade actions denied with:

  * [ ] `deny_code: EMAIL_REVERIFY_OVERDUE`
* [ ] Reduce-only actions remain allowed if policy config says so.

### C3) Reverify request flow

* [ ] Reverify trigger exists (same resend endpoint is fine).
* [ ] Reverify email differs clearly (copy + reason logged).
* [ ] Verify endpoint refreshes `emailReverifyDueAt` again.

### C4) Audit coverage

* [ ] `EMAIL_REVERIFY_REQUESTED`
* [ ] `EMAIL_REVERIFY_VERIFIED`
* [ ] `EMAIL_REVERIFY_LOCK_APPLIED`
  All with identity metadata (IP/user agent/session).

## D. SMS validation requests (Twilio Verify)

### D1) Eligibility gating (NOT baseline)

* [ ] Policy enforces: SMS can start only if:

  * [ ] accountState is `ACTIVE_VERIFIED`
  * [ ] contender eligibility met (Path1 OR Path2) OR admin flagged as SMS-eligible
* [ ] Non-eligible returns:

  * [ ] `deny_code: SMS_NOT_ELIGIBLE`

### D2) Twilio integration correctness

* [ ] Env vars exist (names can vary):

  * [ ] TWILIO_ACCOUNT_SID
  * [ ] TWILIO_AUTH_TOKEN
  * [ ] TWILIO_VERIFY_SERVICE_SID
* [ ] Endpoint exists: `POST /api/sms/verify/start`:

  * [ ] checks policy `PHONE_VERIFY_START`
  * [ ] normalizes phone E.164
  * [ ] calls Twilio Verify “send”
  * [ ] increments daily counters & last sent timestamp
* [ ] Endpoint exists: `POST /api/sms/verify/confirm`:

  * [ ] checks policy `PHONE_VERIFY_CONFIRM`
  * [ ] calls Twilio Verify “check”
  * [ ] on success sets `smsVerifiedAt` and updates contender tier if needed

### D3) Anti-abuse and lockouts

* [ ] Daily cap enforced (e.g., 3/day) → `SMS_RATE_LIMIT`
* [ ] 60s cooldown enforced for OTP sends → `SMS_RATE_LIMIT`
* [ ] Max attempts enforced (e.g., 6) → `SMS_OTP_TOO_MANY_ATTEMPTS`
* [ ] Attempt counts stored and reset logic defined:

  * [ ] `smsVerifyFailCount`
  * [ ] `smsSendCountDay`
  * [ ] `smsLastSentAt`

### D4) Audit coverage

* [ ] `SMS_VERIFY_STARTED`
* [ ] `SMS_VERIFY_START_DENIED`
* [ ] `SMS_VERIFY_CONFIRMED`
* [ ] `SMS_VERIFY_FAILED` (with attempt number)
* [ ] `SMS_VERIFY_LOCKED` (max attempts hit)
  Fields captured: userId, ip, userAgent, phone last-2 masked, sessionId, correlationId.

## F. Tiered matching (Candidate / Performer / Selected)

### F1) Schema requirement (must exist)

* [ ] `users.userTier` exists (string enum):

  * [ ] CANDIDATE
  * [ ] PERFORMER
  * [ ] SELECTED
* [ ] Migration exists and default is `CANDIDATE`.

### F2) Tier assignment logic (backend)

* [ ] A backend function computes contender eligibility using the exact criteria:

  * Path1: age ≥ 30d AND balancePctOfStart ≥ 1.2 AND tradesLifetime ≥ 30
  * Path2: age ≥ 90d AND last trade ≤ 14d AND returnLast90d ≥ 10% AND tradesLast90d ≥ 20
* [ ] Output stored (at least one of):

  * [ ] `user_verification.contenderTier = CANDIDATE_SMS_REQUIRED` when eligible

* [ ] A deliberate admin step moves PERFORMER → SELECTED (do not auto-select).

## K. Verification engine tie-in: “Hedge-fund grade” correctness tests

### K1) Email enforcement tests

* [ ] Create user unverified, set createdAt = now-15 days → trade open should deny with `EMAIL_UNVERIFIED_GRACE_EXPIRED`.
* [ ] Verify email → trade open allowed.
* [ ] Set emailVerifiedAt = now-40 days and emailReverifyDueAt = now-10 days → if overdue grace exceeded, deny with `EMAIL_REVERIFY_OVERDUE`.

### K2) SMS eligibility tests

* [ ] Verified email but NOT eligible → SMS start returns `SMS_NOT_ELIGIBLE`.
* [ ] Eligible (Path1 or Path2) + verified email → SMS start allowed.
* [ ] Exceed daily send cap → `SMS_RATE_LIMIT`.
* [ ] Exceed OTP attempts → `SMS_OTP_TOO_MANY_ATTEMPTS`.

### K3) KYC gating tests

* [ ] Not selected and not invited → KYC view returns `KYC_NOT_SELECTED`.
* [ ] Admin invites → KYC view allowed; status shows INVITED.
* [ ] Submit then approve → KYC view allowed; status APPROVED; payout currency set allowed.

### K4) Audit completeness tests

For each deny above:

* [ ] Audit record exists with deny_code
* [ ] Includes ip + userAgent + timestamp
* [ ] CorrelationId present for multi-step flows (OTP and email verify), if implemented.
