## C. Server — CAPTCHA P1: Session-bound enforcement (must be un-bypassable)

### C1. Slider endpoints exist and are mounted

**Expectation**

* Backend responds to:

  * `POST /api/captcha/slider/start`
  * `POST /api/captcha/slider/complete`
  * `POST /api/captcha/slider/reset` (optional but expected)
* These endpoints write session state (e.g., `req.session.captchaSlider`)

**Where**

* Either:

  * `server/routes/captchaSlider.ts` + mounted in `server/routes.ts`, OR
  * inline in `server/routes.ts`

**Audit steps**

1. Check route registration in `server/routes.ts`:

   * Look for `app.post("/api/captcha/slider/start"...`
   * or `app.use("/api/captcha", captchaSliderRouter)`
2. Confirm express-session typing includes `captchaSlider`.
3. Runtime proof:

   * Call start endpoint, confirm response includes `captchaId`.
   * Ensure session cookie set and subsequent complete call works only with same session.

**Failure signatures**

* `404` on slider endpoints.
* Start works but complete always returns mismatch (cookie/session not persisted).

### C2. Slider complete writes server-verified timestamp

**Expectation**

* `req.session.captchaSlider.verifiedAtMs` is set on complete.
* There is TTL enforcement (issue TTL, verify TTL).

**Audit steps**

* Code inspection:

  * In `/complete`, confirm checks:

    * captchaId matches session
    * issue age < TTL
    * writes verifiedAtMs
* Runtime proof:

  * Start → complete → register should succeed.
  * Start → wait beyond TTL → complete fails with `CAPTCHA_EXPIRED`.

**Failure signatures**

* UI slider completes but register still fails `CAPTCHA_REQUIRED` → session not being marked verified or consumed early.

### C3. Register endpoint blocks when slider not verified (P1 must be server enforced)

**Expectation**

* In `/api/auth/register`, when:

  * `signup_captcha_enforce=1` AND `captcha_provider='SLIDER'`
  * then register must reject unless session has verified slider state.
* Must not rely on any client boolean.

**Audit steps**

1. Inspect `/api/auth/register`:

   * There is a branch:

     * If provider is SLIDER → require verified slider state.
     * Else → verify token (turnstile/hcaptcha).
2. Runtime bypass test:

   * With enforce on + provider SLIDER, attempt register without calling slider complete:

     * Expect HTTP 400 with `CAPTCHA_REQUIRED` (or equivalent).
   * Try sending fake `captchaToken`:

     * Must still fail if provider SLIDER.

**Failure signatures**

* Register succeeds without slider completion → critical security bug (client-only gating).

### C4. Audit logging exists for slider issuance and verification

**Expectation**

* Events recorded (either identityAudit / auth_events / adminActions):

  * `CAPTCHA_ISSUED`, `CAPTCHA_VERIFIED`, and optionally `CAPTCHA_EXPIRED`, `CAPTCHA_RESET`

**Audit steps**

* Confirm calls to audit logger inside `/start` and `/complete`.
* Verify DB:

  * `SELECT * FROM identity_audit WHERE type LIKE 'CAPTCHA_%' ORDER BY created_at DESC LIMIT 20;`

**Failure signatures**

* No audit rows; or category/type mismatched.

## D. Server — P2 Phone enforcement + normalization (must be enforced server-side)

### D1. Register enforces phone when `signup_phone_enforce=1`

**Expectation**

* In `/api/auth/register`:

  * Reads config value
  * If enabled: phone missing → rejects with `PHONE_REQUIRED`
  * If phone provided: validates with libphonenumber and stores E.164 or rejects `PHONE_INVALID`

**Audit steps**

1. Inspect register handler:

   * Must normalize:

     * `parsePhoneNumberFromString(phone, countryIso2)`
     * `isValid()`
     * store `parsed.number` (E.164)
2. Runtime tests:

   * Set `signup_phone_enforce=1`
   * Attempt register without phone → must fail.
   * Attempt register with invalid phone → must fail.
   * Attempt register with valid phone → must succeed and phone stored normalized.

**Failure signatures**

* Enforce toggled but server accepts missing phone.
* Phone required in UI but server doesn’t enforce (or vice versa).
