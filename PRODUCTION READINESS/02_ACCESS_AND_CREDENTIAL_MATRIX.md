# Access And Credential Matrix

Last updated: 2026-03-09

## Purpose

This document lists every access path and credential needed to execute the deployment program. It is ordered by dependency so setup work can proceed without deadlock.

## Required Access

| System | Why It Is Needed | Minimum Access Level | Needed By | Provided By |
|---|---|---|---|---|
| GitHub repository | workflows, branch protection, environments, PR automation | repo admin or equivalent | CI/CD setup | you |
| GitHub Packages / GHCR | image push and pull | package publish for repo | release workflow | you |
| OVHcloud account | server bootstrap, public IPs, networking, anti-DDoS | org-level or delegated admin for dedicated servers and networking | platform bootstrap | you |
| OVH bare-metal servers | OS hardening and RKE2 install | root or sudo SSH | platform bootstrap | you |
| DNS provider | staging/prod records, ingress cutover, ACME | zone admin | ingress/TLS/go-live | you |
| Twilio | SMS OTP and production messaging path | admin or messaging-service admin | credential load and verification | you |
| Resend | outbound email verification path | admin | credential load and domain verification | you |
| Twelve Data | live quote provider | active API key with sufficient rate limit | provider cutover | you |
| Alerting destination | pager/email/webhook receivers | admin or integration owner | observability go-live | you |

## GitHub Access Detail

You need the ability to:

- enable Actions
- create GitHub Environments:
  - `staging`
  - `production`
- configure environment protection rules
- set repository variables or secrets if needed
- enable branch protection on `main`
- allow OIDC for cosign signing and any future cloud federation
- allow package publishing to GHCR

## OVH Access Detail

You need the ability to:

- view and manage dedicated servers
- set or inspect public IP and failover IP assignments
- manage vRack/private network if used
- inspect or configure anti-DDoS/network protection
- inspect or manage reverse DNS if required
- provide server rescue access if initial provisioning fails

## SSH And Operator Access

At minimum, I need:

- hostnames or public IPs for all nodes
- the SSH username to use
- root or sudo access
- confirmation of whether SSH is direct or via bastion/VPN
- source IP/CIDR that should be allowed through host firewalls

## Bootstrap Dependency Order

1. GitHub repo admin access
2. OVH server and SSH access
3. DNS access
4. Twelve Data / Twilio / Resend credentials
5. operator workstation tool install
6. secret generation and SOPS bootstrap
7. OVH cluster bootstrap
8. GitHub workflow and environment setup
9. staging deployment
10. production promotion

## Least-Privilege Recommendations

- GitHub:
  - keep `main` protected
  - require PRs for overlay promotion
  - restrict environment approval for `production`
- OVH:
  - use separate operator accounts where possible
  - restrict SSH ingress to known operator IPs or VPN
- Twilio / Resend / Twelve Data:
  - use purpose-specific production API keys
  - keep access to key rotation limited to operators who manage production cutover
