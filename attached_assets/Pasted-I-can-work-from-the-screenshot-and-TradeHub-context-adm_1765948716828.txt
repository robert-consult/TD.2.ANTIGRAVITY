## What belongs in System Config (and why)

### 1) Platform Mode and Kill Switches (operational safety)

**Purpose:** Immediate, system-wide operational controls that do not change risk *values*, but can stop damage fast.

**UI Card: “Platform Mode”**

* **Maintenance Mode** (toggle): disables trading UI for non-admins; shows banner.
* **Trading Halt (Kill Switch)** (toggle): *block new orders platform-wide*; optionally allow “close-only”.
* **Read-only Mode** (toggle): allow login + analytics, but no order placement.
* **Reason / incident note** (text, required when toggles change) + “Last changed by / at”.

This aligns with exchange/broker risk control patterns where “pre-trade controls” and connectivity/heartbeat considerations are treated as system-level safeguards. ([Federal Register][1])

---

### 2) Market Data and Quote Pipeline Controls

You already have **Quote Refresh Rate (ms)**; expand to cover *staleness, throttles, and caching*, which directly affects fills, PnL accuracy, and user-perceived latency.

**UI Card: “Market Data & Quotes”**

* **Quote Refresh Rate (ms)** (existing)
* **Stale Quote Threshold (ms)**: if last quote older than X → block fills / block new orders / warn.
* **Cache TTL (ms)**: server-side caching window for identical quote requests.
* **Provider Failover Mode**: (Forge primary → fallback) + “Test connection”
* **Rate-limit guardrails**: max quote requests per user per minute / concurrent requests (protects your API + infra). Rate limiting and concurrent request caps are standard for market data APIs. ([Market Data][2])

---

### 3) Execution Engine and Simulation Parameters (system-wide behavior)

These settings define *how* orders are simulated/executed, not *whether a user is allowed* (that’s Trade Settings + per-user overrides).

**UI Card: “Execution Model”**

* **Latency Injection**: min/avg/max (ms)
* **Slippage Model**: off / fixed / volatility-based + max slippage (points/pips)
* **Spread Model**: fixed / dynamic
* **Partial Fills**: enable/disable (if you simulate them)
* **Price Band / Reasonableness Checks**: reject orders outside X% / X points of last quote (protects against “bad ticks” and bad inputs)

Price checks / bands and order evaluation controls are widely used risk controls in electronic trading venues. ([New York Stock Exchange][3])

---

### 4) Risk Engine Enforcement Mode (not the limit values)

Given your architecture rule:

* **Trade Settings** = global limits (platform-wide defaults)
* **User Management** = per-user ability to exceed global limits (stress test exceptional traders)

System Config should hold *enforcement behavior*:

**UI Card: “Risk Enforcement”**

* **Enable Limit Checking** (master toggle): if off, Trade Settings/User overrides won’t block orders (dangerous; admin-only).
* **Enforcement Mode**: hard reject vs warn-only (warn-only should be non-production)
* **Order Throttle**: max orders/sec per user (prevents spam and protects engine)

This matches how professional platforms treat “apply limits” and pre-trade controls as configurable enforcement. ([Trading Technologies Library][4])

---

### 5) Observability, Auditability, and Retention (admin-grade operations)

You already have a “Trade Audit” tab; System Config should control *logging/audit plumbing* and retention windows.

**UI Card: “Audit Logs & Retention”**

* **Audit logging enabled** (toggle): include config changes, admin actions, and security events
* **Retention Policies** (days):

  * audit logs
  * trade/order logs
  * quote snapshots (if stored)
* **Export Controls**: export to CSV/JSON, or push to storage bucket (if supported)

Audit logs are standard for tracking configuration and admin activity, and log retention is typically driven by operational and compliance needs. ([Exabeam Documentation Portal][5])

---

### 6) Security and Admin Access Controls

**UI Card: “Security”**

* **Admin session timeout (minutes)**
* **MFA required for admins** (toggle)
* **IP allowlist for admin** (optional)
* **API key rotation policy** (days) + “Rotate now” (if you support it)

(If you later target broker/dealer compliance, this becomes non-negotiable; even for a sim platform, it reduces operational risk.)

---

### 7) Background Jobs and System Health (performance + reliability)

This is especially relevant if you have quote polling workers, leaderboard recomputation, nightly resets, etc.

**UI Card: “Jobs & Scheduling”**

* Quote poller interval (if different from UI refresh rate)
* Worker concurrency (pollers, settlement, leaderboard)
* Job run windows (avoid peak hours)
* “Run now” buttons (admin-only): recompute leaderboards, resync instruments, cleanup stale sessions

**UI Card: “System Health”** (read-only metrics)

* last quote timestamp
* API latency (p50/p95)
* DB latency
* queue depth / job failures
* error rate

---

### 8) Feature Flags and Remote Configuration

This lets you ship/rollback features without redeploying—useful for a platform that will evolve quickly (and for your “stress test exceptional traders” workflow).

**UI Card: “Feature Flags”**

* flag name, status, targeting (all / admins / specific users)
* rollout percentage
* audit trail for flag changes

Feature flags are widely used to enable/disable features without code changes or redeploys. ([LaunchDarkly][6])

## Persistence design (so changes actually “stick”)

If you want changes to persist and apply consistently, use a single source of truth:

* `system_config` table: `{ key, value_json, value_type, updated_by, updated_at, version }`
* `system_config_audit` table: `{ key, old_value, new_value, changed_by, changed_at, reason }`

This also gives you the auditability you’ll eventually need for a real-money evolution path.
