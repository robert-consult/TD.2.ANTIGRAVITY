# 1) Admin “View As” — Core Security & Compliance (Primary Focus)

## 1.1 Authorization & Access Control

**Checklist**

* [ ] Only **real admins** can start/stop View As:

  * API rejects non-admin users with `403`
* [ ] View As cannot be started while already impersonating (or requires explicit stop first).
* [ ] View As cannot impersonate:

  * other admins (recommended)
  * system/service accounts
  * locked/disabled accounts (policy-defined)
* [ ] AdminGuard explicitly blocks admin routes if `req.user.impersonated === true`.

**PASS if:** Documented test shows:

* non-admin start fails
* impersonated session cannot access `/admin/*`
* “admin-as-admin” impersonation is prevented or safe-lowered to user role

---

## 1.2 Impersonation Session Model

**Checklist**

* [ ] Confirm the impersonation mechanism is **server-authoritative**, not just client UI:

  * Either server-issued impersonation JWT with claims OR server session cookie swap
* [ ] Impersonation identity has **dual-identity** captured:

  * `acting_user_id` (admin)
  * `effective_user_id` (target)
* [ ] Impersonation has a strict **TTL** (e.g., 15 minutes) and expires automatically.
* [ ] Impersonation can be reliably terminated:

  * Stop endpoint works
  * UI “Exit View As” always restores admin context

**PASS if:** You can demonstrate:

* start returns a new session context
* actions in impersonation show the target user’s views/data
* after TTL, system forces exit or re-auth

---

## 1.3 Write Blocking & Safety Rails

**Checklist**

* [ ] While impersonating, **writes are blocked** globally by default:

  * POST/PUT/PATCH/DELETE return `403`
* [ ] If exceptions exist (support notes), they are:

  * minimal
  * explicitly allow-listed
  * separately audited
* [ ] Sensitive actions are blocked regardless:

  * withdrawals, payout requests, trade execution overrides, risk settings changes, password changes

**PASS if:** Automated tests or manual checks prove write endpoints return 403 during View As.

---

## 1.4 Audit Logging (Non-Negotiable)

**Minimum required fields** (must be stored and queryable):

* `admin_id`
* `user_id` (target)
* `action_type` (VIEW_AS_START, VIEW_AS_STOP, VIEW_AS_EXPORT_*)
* timestamp
* source IP
* user-agent
* request correlation id (if available)
* metadata (JSONB)

**Checklist**

* [ ] On START:

  * one row inserted into `admin_actions`
  * metadata includes target identifiers
* [ ] On STOP:

  * one row inserted with stop reason/time
* [ ] On privileged exports or sensitive reads while impersonating:

  * export events are logged (CSV/JSON snapshot exports)
* [ ] Logs are tamper-resistant at least operationally:

  * append-only semantics
  * no admin UI edit/delete for logs

**PASS if:** You can show DB rows for start/stop and export actions with correct metadata.

---

## 1.5 UI Required Indicators (Prevent “Silent Impersonation”)

**Checklist**

* [ ] Global banner appears on every page during impersonation:

  * “VIEW AS ACTIVE”
  * target identifiers displayed (id/email/username)
  * “Exit View As” button
* [ ] Banner cannot be dismissed except by stopping impersonation.
* [ ] Admin UI prevents accidental confusion:

  * visually distinct theme or warning color
  * optional watermark

**PASS if:** Banner persists across routes, reloads, and is correct for target identity.

---

## 1.6 Identity Propagation to All Requests (Traceability)

**Checklist**

* [ ] Every server log line and audit event can be correlated:

  * include `request_id` (from gateway or generated middleware)
* [ ] During impersonation, server logs include:

  * `acting_admin_id`
  * `effective_user_id`

**PASS if:** A single request can be traced end-to-end and attributed to the admin + target.

---

## 1.7 Data Segregation & Leakage Tests

**Checklist**

* [ ] While impersonating User A, the admin cannot accidentally see User B:

  * verify every user-scoped endpoint uses `req.user.id` (effective)
* [ ] Admin-only bulk endpoints are inaccessible in impersonation mode.
* [ ] Exports do not include extra fields not normally accessible to the user (unless explicitly an admin snapshot export route).

**PASS if:** Requests return only effective user data; admin endpoints blocked.

---

## 1.8 Recovery & Failure Modes

**Checklist**

* [ ] If browser refresh occurs in impersonation mode:

  * banner still shows
  * stop works
* [ ] If start call succeeds but redirect fails:

  * admin can still stop impersonation from admin page via status endpoint
* [ ] If stop endpoint fails:

  * system provides fallback “restore admin session” path

**PASS if:** No “stuck in impersonation” states exist.
